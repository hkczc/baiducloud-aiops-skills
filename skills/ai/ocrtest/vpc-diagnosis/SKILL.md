# VPC 网络诊断

## 何时使用

当用户咨询以下问题时，应使用本技能：

- 无法连接云服务器（SSH、RDP）
- 云服务器之间无法通信
- VPC 内网络异常
- 无法访问公网
- 无法访问其他 VPC
- VPN、专线、Peering 网络异常
- NAT Gateway 配置问题
- 安全组或网络 ACL 配置问题
- 路由配置问题
- DNS 解析异常
- 网络延迟、丢包等问题

---

## Instructions

收到用户请求后，请按照以下步骤进行分析。

### 1. 明确问题

首先理解用户遇到的问题，例如：

- 网络不通
- SSH 超时
- Ping 不通
- DNS 无法解析
- 连接被拒绝
- 网络速度慢

如果问题描述不明确，应先询问用户，而不是直接分析。

---

### 2. 收集信息

尽量获取以下信息：

- 地域
- VPC ID
- 子网 ID
- 实例 ID
- 源 IP
- 目标 IP
- 使用协议（TCP、UDP、ICMP）
- 使用端口
- 错误提示
- 网络拓扑

如果缺少关键信息，应主动询问。

---

### 3. 按照固定顺序排查

依次检查：

1. VPC 是否正确
2. 子网配置是否正确
3. IP 是否属于对应网段
4. 路由表是否正确
5. 安全组规则是否放通
6. Network ACL 是否拦截
7. NAT Gateway 是否正常
8. Internet Gateway 是否正常
9. VPN 或 Peering 是否建立成功
10. DNS 是否配置正确
11. 实例是否运行
12. 服务是否监听对应端口
13. 操作系统防火墙是否放通

不要跳过前面的步骤。

---

### 4. 分析原因

根据已有信息，列出最可能的原因。

按可能性从高到低排序。

如果无法确定，应明确说明原因，并说明还需要哪些信息。

不要进行无依据的猜测。

---

### 5. 给出解决建议

对于每一个可能原因，都需要提供对应的解决方案。

例如：

- 修改安全组规则
- 添加路由
- 修正下一跳
- 开启 DNS
- 修改 NAT 配置
- 放通系统防火墙
- 检查实例监听端口

建议应具有可操作性。

---

## Output

回复应包含以下几个部分：

### 问题分析

简要总结用户的问题。

### 可能原因

按照可能性排序列出原因。

### 排查建议

提供具体检查步骤。

### 解决方案

针对问题给出修复建议。

### 后续需要的信息（如有）

如果无法定位问题，应明确说明还需要哪些信息。

---

## Guidelines

- 使用专业、准确、简洁的中文。
- 不要在信息不足时直接下结论。
- 不要假设用户的网络架构。
- 优先根据用户提供的信息进行分析。
- 排查过程应遵循"网络配置 → 路由 → 安全策略 → 网络设备 → 实例 → 应用"的顺序。
- 如果存在多个可能原因，应按概率排序。
- 对于每个原因，都应给出对应的验证方法和解决建议。
